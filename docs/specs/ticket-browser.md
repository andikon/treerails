## Problem Statement

Tree Rail's GitHub ticket picker becomes difficult to use in a repository with many issues. A flat list of numbers, open/closed states and titles does not show the labels and discussion needed to decide which ticket to work on. Developers must repeatedly leave the tool to find issues assigned to them, inspect readiness labels, read comments and contribute to the discussion. The current first-100-issues limit can also hide the right ticket entirely.

One developer coordinating coding agents needs a persistent, repository-specific way to find work without losing sight of tickets already being worked on. Reading an issue should not create local tasks or launch an agent. When the developer does start a new agent conversation, decisions recorded in issue comments must be included in the approved starting context, even when the full discussion is too large for an inline launch prompt.

## Solution

Replace the ticket picker with a two-pane ticket browser. The left pane remains one ticket column: a bounded, collapsible Active section above the selected saved view's filtered results. Cards show issue number, title, open/closed state and labels, with local-work/agent indicators in Active. The right pane previews the selected issue's description and chronological discussion using readable terminal Markdown.

Offer guided filters and multiple named saved ticket views per repository. Remember each view's criteria and order, the repository's last active view and Active collapse preference. Fetch matching issues from GitHub in pages rather than filtering an arbitrary initial subset. Keep selected content stable during background refresh and support clearly marked cached reading when GitHub is unavailable.

Provide an open-in-GitHub action and a comment workflow with persistent per-issue drafts, review and explicit posting. Enter opens the selected ticket's existing task/session workspace. New agent conversations receive a freshly captured, approved, complete discussion snapshot as a retained Markdown document with a short starting prompt. Continuing an existing conversation does not replay that context.

A Ticket remains a GitHub Issue. A Task remains a local workstream within a ticket. GitHub issue state, readiness labels, local task progress, agent attention and agent health remain separate concepts. This is inspired by planning boards visually; actual GitHub Projects integration is not required.

## Implementation Decisions

- **Retain domain boundaries.** Tickets are GitHub Issues; tasks and conversations remain local work records. Readiness comes from labels, not a new Tree Rail-owned ticket status or a GitHub Projects field. Issue state, task progress, agent attention and health have separate display labels and meanings.
- **Separate browsing from opening work.** Add a coherent ticket-browser workflow around the existing ticket workflow boundary. Reading lists, metadata, descriptions and comments must not create durable tasks/worktrees/sessions or start the session host. Explicit entry into ticket work keeps existing preparation and ownership rules. Returning restores browser context.
- **Extend the existing GitHub adapter.** Expand the injectable issue source to support repository identity, current identity, label/assignee metadata, filtered issue pages, discussion pages, comment posting and browser opening. Keep network/CLI transport replaceable without replacing workflow or persistence policy. Do not scatter direct GitHub calls across views or create a separate mock-only browser implementation.
- **Add the required data.** Issue summaries need labels, assignees, author, timestamps and comment counts in addition to current identity/title/body/state/URL data. Comments need stable identity, source URL, author, Markdown body, creation/update timestamps and edited information. Query/thread results carry paging, freshness, completeness, errors and correlation information. Snapshot references and comment-send outcomes are distinct from issue metadata.
- **Use repository identities for preferences.** Scope views and drafts to the GitHub host/repository identity within the chosen configuration context rather than a local checkout path. Clones/worktrees of that repository reuse those preferences; unrelated hosts/repositories and explicit configuration contexts remain separate. Me stays symbolic and resolves to the active authenticated identity. Show the posting account during comment review.
- **Implement one column and one preview.** The left column contains Active followed by the current view's filtered results. Either section can drive the shared right preview. Cards show number, title, issue state and named labels; Active adds relevant progress/attention/recovery information. Use wrapping or an explicit overflow indicator for long metadata and show full metadata in preview. Do not rely on color alone.
- **Derive Active from work, not filters.** Include a ticket when a local task is In progress or a managed agent has live/unresolved execution. Ready counts while checkout ownership remains. Historical records or unused worktrees alone do not count. Closed issues can remain active. Resolve membership from current work/ownership rather than every historical failed conversation.
- **Bound and order Active independently.** Active belongs to the selected repository, is collapsible, remembers that preference, exposes count/attention while collapsed and occupies at most roughly one third of the column when expanded. Scroll within it as required. Prioritize Needs input and recovery problems rather than applying the saved view's sort to Active. Show each ticket once; annotate active tickets that also match and distinguish query totals from displayed filtered rows after deduplication.
- **Persist named views.** Each repository starts with Open tickets: open issues, unrestricted labels/assignees, recently updated first. Support create, duplicate, rename and delete, with stable identities and repository-unique names. Restore the last active view. Deletion changes preferences only; deleting the final view restores an Open tickets default.
- **Use a guided filter editor.** Offer Open/Closed/All state; Anyone/Me/Unassigned/specific assignees; included labels with All/Any selection and All default; excluded labels; text and text-search scope; and ordering. Different categories combine with AND, specific assignees with OR, and excluded labels always exclude. No included labels means unrestricted labels. Report contradictory include/exclude choices before Apply. Text must not override structured criteria through embedded query syntax.
- **Make filter persistence deliberate.** Applying validates, updates results and saves current-view criteria/order. Incomplete/canceled edits do not alter the applied view. Duplicate creates another named view rather than a transient branch of the current filter. Show active criteria and text scope above results. Search titles/descriptions by default; an explicit include-comments choice is saved per view. Support recently-updated-first, newest-created-first and oldest-created-first ordering.
- **Filter remotely and page honestly.** The remote query is restricted to the selected repository's issues and full saved-view criteria before display paging. Load further matching pages near the loaded end. Carry paging/completeness metadata and stable issue identity through sorting and deduplication. A limited first page, failed request or GitHub search result ceiling must never be described as an exhaustive view or empty repository. Show total matches only when available and explain limits that require narrower criteria.
- **Correlate asynchronous results.** Scope completions to the repository, view/query revision and selected issue/request they belong to. Ignore superseded results instead of letting a slow old query or discussion request replace a newer selection. Preserve loaded rows through page failures and distinguish end, loading, error and incomplete states.
- **Preserve reading during refresh.** Refresh in the background and on explicit request without interrupting typing, selected-issue identity or the reading anchor. If background refresh removes an issue from the filter, keep its preview with a no-longer-matches notice until another selection. An explicit view switch or Apply retains selection only when still visible in Active/results; otherwise select the first visible ticket or show an empty preview. Drafts remain independent of selection.
- **Keep a real browser cache.** Cache fetched query results and issue discussion independently of durable ticket/task/session work. Associate cached data with its repository, query, identity context, freshness and completeness. A cache of previously opened work tickets is not a substitute for a cached query. Mark stale/incomplete content explicitly; do not show an old query's cache as fresh results for newly applied criteria. No cache means unavailable/not cached, not zero matches. Existing hosted work and local drafts remain accessible; posting and fresh context capture require connectivity.
- **Render discussion as terminal Markdown.** Show issue metadata and description, followed by comments oldest first, with author, timestamps and edited markers. Render headings, lists, checkboxes, quotes and code blocks readably, with links/images/attachments represented as references. Progressive body/comment loading may support preview reading, but must expose incomplete state. Preserve comment identity and reading anchors through refresh; confirmed posting reveals the new comment.
- **Make comment target and identity explicit.** A comment draft belongs to a repository/issue. Review fixes its target and exact text and shows the active posting identity. Background navigation cannot redirect a reviewed comment to another issue. Leaving the editor retains its draft; explicit discard removes it. Restoring a draft never posts it.
- **Model send outcomes honestly.** Distinguish confirmed posting with a returned comment identity/URL, definitive rejection and indeterminate delivery. Confirmed success clears the draft and reveals the comment; definitive failure keeps the draft and error. An indeterminate response persists a confirmation-unknown state and draft through restart. Refresh discussion to show possible matches for verification, but text similarity is not proof of success. Require explicit resolution/retry and never automatically replay an uncertain send.
- **Use contextual keyboard actions.** In the browser use f for filters, v for saved views, c for commenting, o for GitHub, a for Active collapse, R for refresh and ? for actions. Enter explicitly enters ticket work. Ctrl+s applies filter edits or reviews a comment; y posts only from comment review. Ordinary characters/paste belong to the active editor. Existing ticket-workspace, basic-worktree and agent-input meanings remain in their contexts. Narrow layouts show the focused pane. Legends advertise only non-obvious actions handled by the current owner, fit whole hints and omit routine Vim navigation/search/input reminders.
- **Capture a complete discussion for each new conversation.** Before starting-brief review, fetch the accessible issue description and every current comment page to completion. Build a frozen Markdown discussion document with author/timestamp/source information. A partially loaded preview, failed page or unavailable GitHub connection cannot be approved as a complete fresh capture. Full discussion means current accessible description/comments and their textual references, not deleted history, downloaded attachment binaries or the complete GitHub event timeline.
- **Freeze what is approved.** The starting review covers the exact captured document plus issue/task/checkout context and optional handoff. Associate approval with that immutable document's identity/content, not a mutable preview cache. Later comments cannot silently rewrite it. Re-fetching or replacing context requires new review. Each later new conversation captures fresh discussion. New-start retries and handover use the approved document while retaining existing task/worktree ownership checks.
- **Retain snapshots outside worktrees.** Store authoritative approved Markdown documents in Tree Rail's data area and retain references/identity/completeness information in combined configuration. Preserve artifacts after checkout cleanup and do not silently replace missing/modified documents with the current thread. This explicitly extends the earlier single-file persistence decision for discussion bodies only. Settings, views, drafts and other remembered state remain in the combined configuration; document this exception in the architecture record.
- **Validate complete-document delivery.** Supply the retained full document through a provider mechanism proved on the supported Copilot version, accompanied by a short starting prompt. Passing the whole thread as one launch argument, increasing an inline-size cap or making a file available without proving provider delivery is insufficient. Keep document bodies out of bounded launch arguments and control-message payloads. If the provider cannot receive complete context, block that new start with an actionable explanation instead of truncating, summarizing or starting with partial context. Preserve approval and ownership through delivery failures.
- **Do not replay or inject discussion implicitly.** Continue reattaches/resumes the selected recorded conversation without resending a starting brief. Browsing, commenting and label/assignee refresh do not inject instructions into a live agent or trigger an issue-body requirements revision. Existing explicit requirements revision remains a separate action.
- **Preserve persistence compatibility.** Extend combined settings/state without destructive migration and preserve comments, unrelated fields and concurrent changes. View identity must survive rename; draft/send/snapshot-reference updates must not overwrite unrelated preferences. Surface same-view conflicts. Respect explicit configuration isolation. Treat browser caches as derived data, while approved discussion artifacts are retained context with durable references.

## Testing Decisions

The user confirmed this testing approach before publication.

- **Primary boundary:** prefer the existing ticket-workflow command/event API, extending its injectable GitHub source for filtered pages, discussions and comment posting. Exercise real workflow rules and persistence through that high-level boundary, driving application actions/completions where appropriate. Avoid new independent test facades for every view or field.
- **Test external behavior:** assert returned state/events, visible interaction results, durable data after reopen, explicit network mutations and preserved ownership/context. A test should detect a user-visible failure such as a missing second-page match, lost draft, duplicate send or changed approved document; do not mirror private helper algorithms or couple tests to incidental call ordering.
- **Existing prior art:** reuse the current ticket preparation/reopen tests with an injected issue source, requirements refresh/offline tests, configuration/concurrent-draft tests, application interaction tests, Ratatui buffer rendering tests and controlled host/provider lifecycle/recovery tests. Preserve the existing real disposable-Git approach where worktree and cleanup behavior is relevant.
- **Filtering and saved views:** cover two repositories, restart restoration, view CRUD/default fallback, ordering, All/Any/excluded labels, assignee modes, text scopes, invalid/canceled edits, configuration isolation and repository identity across local paths. Verify requests apply constraints before paging and that late completions cannot replace another view.
- **Paging and cache:** cover matching issues beyond page one, duplicates across refresh/pages, missing totals, result ceilings, rate limits, failed next pages, uncached/offline queries, stale/incomplete cache, changed authentication context and a distinction between zero matches and unavailable data.
- **Active projection:** cover in-progress tasks, live agents, Ready ownership, Needs input, unresolved execution, historical-only records, closed-but-active issues, filtered-out active work, repository scoping, deduplication and count meanings. Check bounded/collapsed rendering and attention ordering through visible output.
- **Preview and selection:** exercise full Markdown examples, long/unicode metadata, many comments, source references, edited/deleted-author presentation, incremental loading, reading-anchor preservation, selected issues leaving a filter and intentional view changes. Inject out-of-order completions.
- **Comment lifecycle:** exercise compose, review, explicit send, fixed repository/issue/account display, ordinary letters/paste, cancel/discard, per-issue restart restoration, confirmed success, definitive permission/rate-limit errors and response loss after remote creation. Simulate restart while confirmation is unknown, show candidate matches without automatically treating them as proof, and verify no automatic retry/publication.
- **Persistence and artifact integrity:** use real temporary storage to verify combined-file compatibility, preserved comments/unrelated edits, multiple clients, same-view conflicts, immutable retained document contents, missing/changed references and survival of worktree removal. Previewing alone must not create tasks, claims or host processes.
- **Session integration:** reuse existing host/provider command/event tests with controlled providers to cover approval, same-request retry, failure before launch, handover, continued ownership on uncertainty, exact artifact reuse and Continue without brief replay. Include full multi-page documents larger than current inline launch limits; assert the complete bytes/references are supplied without putting the body back into bounded arguments.
- **Provider compatibility proof:** separately validate and record complete initial-document delivery on the supported Copilot version and native platform before claiming that route works. A fake provider proves orchestration behavior, not real Copilot attachment semantics. Routine CI uses controlled local children/providers and never posts to real GitHub issues or starts paid agent work.
- **TUI interaction/rendering:** reuse the application key-routing and Ratatui test backend at wide and narrow sizes. Verify focus ownership, Active/filtered selection, modal/editor routing, exact contextual shortcuts, no routine navigation legends, whole-hint fitting and no child-only/global actions advertised in the wrong mode. Prefer focused behavior assertions over full-screen snapshots that merely freeze layout details.
- **Regression scope:** retain the current basic Git/worktree, ticket preparation, explicit requirements revision, agent detach/reattach/resume, cleanup, notifications and read-only CLI listing guarantees. Browser queries and drafts must not accidentally start the host or alter local work.

## Out of Scope

- Actual GitHub Projects boards, custom board Status fields, multiple kanban columns or board automation.
- A new local ticket-status system, automatic issue progression or label creation inferred from a view name.
- Editing/deleting existing GitHub comments; open GitHub for those actions.
- Creating/editing/closing issues, assigning people, changing labels or posting reactions from this browser.
- Browser-identical rendering, embedded web content, inline image rendering, downloaded attachment binaries and the entire GitHub event timeline.
- Deleted comment/revision history or discussion content the authenticated user cannot access.
- Raw GitHub query editing or a new general-purpose query language in this first version.
- Cross-repository Active aggregation, separate worktrees per task, or changing current checkout ownership rules.
- Automatic refinement/implementation/review execution, automatic prompt approval, automatic posting/reposting or automatic injection of new discussion into existing agents.
- Treating a summary, partial comment page or truncated document as the requested full discussion.
- Replacing the existing basic-worktree workflow, redesigning all application keybindings or adding unrelated Git/PR features.
- General artifact garbage collection or transcript management beyond retaining the approved discussion documents and their references required here.

## Further Notes

- This specification synthesizes 24 answered design questions and the confirmed testing approach. The requested top-of-column Active section is explicit: it replaces the earlier suggestion of relying on a separate Active work shortcut.
- Architectural intent remains ticket-native GitHub work with local tasks, one shared ticket checkout and a detachable local session host. The new architecture decisions freeze complete discussion context for new conversations and retain its documents outside configuration/worktrees. The separate-document decision is a deliberate, limited exception to the previous single-file preference.
- Current implementation has a first-100 all-state issue list, sparse issue metadata, no discussion browser, and an inline starting-brief path. The host's current 48 KiB brief guard does not make long inline delivery reliable: Windows limits the entire command line to 32,767 characters, and host control messages have a separate 4 MiB limit. Revalidate the selected delivery mechanism rather than simply raising caps.
- Current provider documentation describes file context and initial attachments, but does not by itself establish compatibility with Tree Rail's previously tested Copilot 1.0.94. Supporting the required file-context path is an implementation validation gate. Completeness means retaining and supplying the complete captured text; it is not a promise about a model's reasoning or undocumented context behavior.
- GitHub search can expose at most 1,000 results for a query; progressive loading must surface any such ceiling rather than pretend to enumerate every repository issue. Reading an issue also does not prove permission to post a comment.
- Primary sources checked during design: [GitHub CLI issue listing](https://cli.github.com/manual/gh_issue_list), [GitHub issue filtering](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests?tool=cli), [GitHub search limits](https://docs.github.com/en/rest/search/search#about-search), [issue comment API](https://docs.github.com/en/rest/issues/comments), [GitHub CLI comments](https://cli.github.com/manual/gh_issue_comment), [Windows process launch limit](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Copilot file context](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/overview#include-a-specific-file-in-your-prompt) and [Copilot CLI options](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#command-line-options).
