## Problem Statement

Tree Rail helps a developer find a project, create or select a Git worktree, and launch a tool, but the developer must separately remember which GitHub issue, unit of work and Copilot conversation belong together. After launch, Tree Rail does not own the interactive terminal, retain the agent's conversation identity, or distinguish an agent working from one requesting input or ready for another instruction.

This becomes difficult when one developer coordinates several tickets. They must hunt through terminals, reconstruct context, avoid two agents editing the same checkout, manually reconnect after closing the explorer, and decide whether an agent finishing a response means the work is done. A clean worktree or closed issue also does not establish that the agent has stopped or that its directory can be removed without disrupting ongoing work.

The developer wants a default ticket-centered workflow that keeps tasks, conversations, worktrees and agent attention together, while preserving the current direct project/worktree/tool workflow.

## Solution

Make project → GitHub ticket the default entry into development. A ticket is always an already-defined GitHub Issue. It contains locally tracked tasks, each of which can have multiple agent sessions. All tasks and sessions for the ticket share its worktree and branch, so implementation and subsequent review can operate on the same changes and the ticket can be delivered through a pull request.

Host the real interactive Copilot terminal inside Tree Rail. A persistent local session host owns live agent processes, terminal state, attention observations and checkout ownership. The CLI application acts as a detachable UI client for this workflow: closing the UI leaves sessions running or waiting, and reopening reconnects to the same live terminal while the host remains alive.

Keep the interaction simple: Running, Needs input and Ready describe session attention; separate health information describes interruption or unavailable observation. Navigation and agent-input modes have distinct colors and explicit text labels. Starting, continuing, handing over, stopping, updating requirements and cleaning up remain deliberate user actions. Automatic refinement/implementation/review cycles are future work.

## Implementation Decisions

- **Domain and ownership:** A project groups its original checkout and linked worktrees. A ticket is an existing GitHub Issue, identified independently of its title or branch. Tasks are local workstreams beneath a ticket, not automatically GitHub checklist items or sub-issues. Agent sessions are provider conversations associated with tasks. A ticket has one associated working checkout at a time, shared by its tasks and sessions. Checkout ownership must be enforced against the actual Git worktree identity across tickets, clients and configuration contexts, rather than only a display path or ticket number.
- **Current scope change:** Native ticket integration expands the existing manual-ticket boundary. Hosting interactive Copilot and retaining its lifecycle expand the current external-terminal handoff. These changes preserve the direct basic workflow and the existing Git-operation policy; this spec does not introduce a broader Git operation queue, history editor or merge engine.
- **Default entry and task structure:** Opening a project leads to ticket selection and a ticket overview. Opening an issue alone launches nothing. Create one task when no explicit breakdown exists. Import an explicit task list through an inspectable action, with stable local identities so later edits do not discard session associations. The issue determines the work structure; there is no fixed ordered workflow. The precise import syntax is an implementation choice that must be documented and must distinguish task lists from acceptance criteria.
- **Workspace association:** First Start work offers the existing creation capabilities or explicit adoption of an existing worktree, with a visible branch, base and destination. Preserve occupied-path refusal, existing-branch/worktree reuse and original-checkout protection. Reject conflicting active ticket associations. Subsequent tasks/sessions reuse the recorded checkout rather than creating another one. Changes or disappearance of the checkout must be reconciled before another managed session starts.
- **Primary new module and seam:** Build a session-host module with one production-facing command/event interface used by the UI client. It coordinates ticket/task/session lifecycle, exclusive checkout ownership, start/continue/new-session/handover/stop operations, attach/detach, input/resize and state snapshots. It owns the policy; the UI does not independently decide that a checkout is available or that a second agent should be launched. Keep PTY, provider, transport and storage mechanics behind that interface, with only dependency-specific internal seams where behavior actually varies.
- **Reuse existing modules:** Reuse the existing terminal-independent Git, discovery, configuration and background-job execution capabilities. Extend GitHub integration using the already-established GitHub CLI approach for issue identity/content/status. Extend configuration/storage for workflow state and the notification setting. Modify application state, rendering, startup and input routing to act as a host client for ticket work. Keep existing launch profiles available for the basic workflow instead of rewriting unrelated Git features as a prerequisite.
- **Hosted terminal module:** Own real interactive PTYs, agent child processes, terminal screen parsing, cursor and alternate-screen state, terminal dimensions, input/paste and bounded scrollback inside the host. Continue reading/parsing output even with zero clients. Implement background I/O so a disconnected or slow UI cannot block a child on terminal output. Select compatible libraries during implementation; this spec does not assert that a particular terminal widget already provides complete process ownership or input forwarding.
- **Copilot integration:** Copilot is the first integrated provider. Preserve the native interactive CLI experience rather than substituting an SDK-only chat UI. Retain exact provider conversation identities and distinguish new-session kickoff from resume. Use an interactive kickoff mechanism for new sessions. Never rely on a globally latest conversation selector to infer ticket identity. A missing saved provider conversation must produce a recoverable result or an explicit new-session choice, not silently create a replacement under a supposedly resumed identity.
- **Continuation:** Continue resolves to the selected/current task's recorded session, visibly identifying the target. Reattach to its live hosted terminal when present; otherwise explicitly resume the retained conversation in the correct worktree. Start new session is separate. Reattachment and resume must not implicitly resend the starting brief or last user instruction. Native provider-reported identity/context changes must be reconciled without silently remapping a task or falsely releasing its checkout ownership.
- **Starting brief:** Retain a snapshot of the issue title/body, task objective, worktree/base context and optional explicit handoff used to begin a session. Expose the brief for inspection. Retain the provider's own context when resuming; do not silently concatenate prior transcripts into a new conversation. Previously recorded Tree Rail-created conversations remain resumable; importing externally created conversations and controlling externally running sessions are deferred.
- **Attention and health:** Running, Needs input and Ready are the three normal attention labels. Ready means the response/processing has finished and the session is available for another instruction; it does not imply task success, issue closure or a terminated CLI. Explicit task progress remains separate. Use reliable provider events, including resolution of outstanding input requests, instead of interpreting a quiet terminal or natural-language answer as definitive activity. Interrupted and Status unavailable are health information, not extra normal attention phases. Losing observations must not fabricate a healthy attention transition or release ownership.
- **Experimental provider observation:** Experimental Copilot event integration is acceptable only after a compatibility test demonstrates the native hosted UI, session correlation, actual human-input waits and resolution, running/ready transitions and failure behavior. Support and document a tested version range. Existing hooks may be useful, but do not assume they provide all paired request-resolution events or a replayable status snapshot. An event bridge failure leaves terminal access available where possible and surfaces Status unavailable; handover still requires verifiable stop. If a viable integration cannot be established, report the limitation rather than claiming completion through guessed states.
- **Input modes:** Navigation mode directs keys to Tree Rail. Enter focuses the selected agent terminal; a visible configurable shortcut returns to navigation mode. Agent-input mode passes ordinary Copilot controls, including Escape and Ctrl+C, to Copilot except for that return shortcut. Provide different mode colors plus explicit text labels and focused-pane indication. Preserve normal form/search input behavior. Other tickets' indicators can update without stealing input focus.
- **Shared-checkout handover:** One managed session may work in a checkout at a time, including across different ticket/configuration records. Different checkouts can work in parallel. A session waiting for input retains ownership. Handover stops the current managed work and preserves its conversation before another task/session acquires the checkout. Verify that the previous managed execution is stopped; failed or uncertain stop keeps ownership and reports the failure. Stopping does not promise rollback of already completed edits or external effects. Unmanaged external tools remain outside Tree Rail's enforcement.
- **Host lifecycle:** Use a persistent local host independent of the UI process. Start it automatically when the ticket workflow needs it, without OS service installation or login startup. UI exit, intentional detach and client disconnection release input control while retaining agent ownership and live terminal state. Stop session and Stop host are explicit actions. A host with no live sessions may exit. The first release supports the current local account and one controlling UI; a second UI requires explicit takeover rather than silent competing input or resize control.
- **Private local protocol:** Provide user-scoped local communication, startup/discovery coordination and a version handshake. The host is authoritative for session ownership and workflow mutations. Commands/results and events must identify their target and correlation identity. A Start whose result was lost must be reconciled/idempotent so a retry cannot spawn a duplicate. Host identity/configuration routing must preserve existing configuration overrides and still enforce ownership across contexts. Avoid exposing an unauthenticated network listener or assuming that a default local IPC endpoint is automatically private.
- **Reattachment:** Return an authoritative snapshot of relevant workflow/session/terminal state followed by ordered updates, coordinated so events during attachment are neither lost nor applied twice. Restore current content, cursor, modes and pending-input information rather than only forwarding future bytes. Keep the last nonzero terminal size while detached and let the controlling UI resize on attachment. Bound queues/history and permit a fresh snapshot for a lagging client instead of unbounded retention. A stale client must lose input control after takeover.
- **Failure and upgrades:** The first survival guarantee covers UI detach/disconnection/ordinary closure while the host and operating-system user session remain alive. It does not promise the same live terminal after host failure, sign-out or reboot. Persist references, mark affected sessions Interrupted, reconcile remaining activity and require explicit resume. Do not automatically restart agents, replay instructions or treat a retained PID as proof of identity/liveness. Incompatible client/host versions must fail usefully without silently restarting a busy host.
- **Workflow state and configuration:** Persist task records, issue identity/cache and synchronization timestamps, starting-brief snapshots, worktree associations and recorded provider session references under the existing combined TOML policy. Preserve settings, comments, unrelated external edits, atomic writes and conflicting-edit behavior. Runtime-only live handles, screen state and bounded scrollback stay in host memory; provider transcripts remain in Copilot's storage. Preserve explicit configuration overrides, saved/temporary source precedence and existing upgrade behavior. Noninteractive listing remains read-only and must not start a host or create/write state. No separate workflow database or disk-persisted terminal/event log is required.
- **Issue synchronization:** GitHub remains authoritative for the ticket. Retain starting-brief snapshots and detect changed issue content/status through explicit or bounded refresh. Show Issue updated and inspectable differences; updating tasks or sending revised requirements is explicit and preserves local identities/progress. GitHub failures do not block local reattachment. Known tickets can use cached content with a visible last-sync timestamp and unavailable/stale information; do not fabricate offline-only tickets or claim fresh issue state. Copilot's network availability is independent.
- **Closure and cleanup:** A closed GitHub Issue, including one closed through a merged PR, is annotated Ticket closed in the ticket and its tasks while retaining prior progress/history. It is not automatic proof that every task succeeded or the agent stopped. Deleting the worktree requires an explicit stop of its managed owner, including a waiting agent. The basic deletion path must honor that ownership too. Preserve dirty-worktree refusal and original-checkout protection; retain the local branch by default, display unpublished local commits, and preserve workflow records after directory removal. Do not implicitly close/reopen GitHub issues or delete records on the user's behalf.
- **Notifications:** Add a persisted opt-in desktop-notification setting accessible through application settings. Notify on actionable Needs input transitions and session failures, including while the UI is detached. Ordinary output, tool calls and Ready transitions remain quiet. In-app attention remains available regardless of desktop settings. Notification delivery is observation only, not automatic approval or progression.
- **Delivery approach:** Begin implementation with a bounded native Windows lifecycle and Copilot/event compatibility spike. Record actual supported versions and launch environments, including ordinary terminal-window closure. Then implement behind the host command/event seam and wire the UI to it. This initial validation is part of delivering the feature, not evidence already obtained. Keep portable module choices and validate supported operating systems in their native environments before asserting compatibility.

## Testing Decisions

- **Primary seam:** Test observable workflow behavior through the production session-host command/event interface used by UI clients. Prefer an attachable client interacting with the host over tests of private registries, process fields, internal channels or state-machine implementation branches. The same seam should cover ticket/task/session actions, observable terminal snapshots, attention/health and ownership outcomes.
- **Existing seams and prior art:** Reuse public Git/configuration/discovery/startup behavior already exercised by the repository. Existing tests use disposable real Git repositories and local bare remotes, streamed real hook output, configuration comment preservation and concurrent-edit scenarios, read-only CLI startup and Ratatui TestBackend rendering. Extend those approaches rather than inventing a parallel mocking layer for the existing Git operations.
- **Controlled dependencies:** Use controlled agent child programs and provider-event fixtures at external dependency interfaces for deterministic host tests, while retaining the real process/PTY and production client interaction where lifecycle is under test. Use controlled GitHub CLI responses for issue changes, cache/offline and authentication failure. Keep tests independent of a paid live model and the developer's real repositories. These fixtures must not bypass the authoritative host command path to install ownership or mark a session ready.
- **Ticket/task/worktree scenarios:** Verify a simple issue becomes one task; criteria are not blindly split; explicit imports are previewable; task IDs and session associations survive issue updates; create/adopt has explicit base/path and collision behavior; separate ticket checkouts can run in parallel; aliasing the same checkout through another ticket/client/configuration cannot start another managed owner.
- **Session identity and briefs:** Verify new versus Continue behavior, live reattachment versus explicit resume, retained kickoff snapshots, explicit handoffs, no transcript copying, no prompt replay during reconnect/resume, correct task/worktree correlation and useful behavior for missing provider conversation identities. Provider identity/context mismatches must not falsely establish or release ownership.
- **Attention, input and handover:** Verify Running/Needs input/Ready transitions through representative provider events, outstanding-request resolution, Ready remaining separate from task completion, and health after lost/lagging observations. A waiting agent must retain ownership. A failed/unverified stop must block handover. A successful handover must prevent the old prompt/session from restarting managed edits in the transferred checkout.
- **Real lifecycle tests:** Start an actual host process and controlled interactive child, detach or terminate the UI client, and reconnect to the same child identity/current terminal without duplicate start. Exercise detachment during heavy output and during a question/permission display, multiple resize dimensions, bounded history, slow clients, snapshot/subscription ordering and explicit input takeover. Closing the UI is not equivalent to stopping the host.
- **Failure and retry tests:** Lose the reply to a successful Start, retry and verify only one child. Test simultaneous host startup, stale endpoints, incompatible versions, client failure, host failure, stop failure and recovery reconciliation. Verify no automatic agent restart or instruction replay after interruption, and no busy-host restart merely because a different UI version connects.
- **Storage/startup regression coverage:** Verify workflow saves preserve comments/settings/unrelated concurrent edits, malformed data is reported without overwriting the document, retained associations survive restart, configuration overrides keep their meaning and noninteractive listing performs no host startup or file mutation. Verify terminal output/transcripts do not leak into persisted workflow state.
- **GitHub/cleanup/notification coverage:** Verify cached known tickets remain usable with visible freshness information; issue updates require explicit application; closure annotates rather than completes tasks; owning sessions must stop before deletion through either UI path; dirty/original protection and branch/history retention remain. Verify notifications default off, persist when changed, fire for Needs input/failures, remain quiet for ordinary Ready/output events and do not control the agent.
- **Focused TUI coverage:** Use the existing terminal test backend and input-event style for project/ticket/session selection, Continue versus New session, form/search routing, mode label/color differences, configurable escape from agent-input mode, ordinary Copilot key/paste forwarding and useful narrow layouts. Keep these tests focused on user-visible routing/rendering rather than duplicating the host's workflow tests for every internal state.
- **Live compatibility gate:** Separately exercise the real installed Copilot CLI in a disposable ticket/worktree, with its event integration and hosted terminal on native Windows first. Verify identity, initial/resumed sessions, native prompts, request resolution, normal completion, cancellation, resizing and UI-window closure. Check relevant launching-terminal/process-supervisor behavior. Validate other claimed platforms in their own environments. Report concrete version/platform results; passing an echo-child fixture does not prove real Copilot compatibility.
- **Good-test standard:** Assert external behavior and durable outcomes: which process remains alive, what the client displays/receives, which checkout remains owned, which Git/config data changed, and whether an action was duplicated. Avoid assertions about private collection layouts, channel counts, implementation-specific call ordering or one-for-one replicas of the code. Use bounded waits and explicit child/event coordination instead of arbitrary sleeps wherever possible.

## Out of Scope

- Creating or refining tickets automatically, AI task decomposition and automatic refinement → implementation → review execution. Tickets are expected to be defined already; future skills can orchestrate this feature later.
- A fixed mandatory set/order of tasks or treating every acceptance criterion as a separate task.
- A separate local ticket system, automatic GitHub issue creation/closure/reopening, or automatic synchronization of local task progress into issue checklists/sub-issues.
- Importing conversations created outside Tree Rail or taking control of externally running Copilot terminals in the first release. Adopting an existing Git worktree remains in scope.
- Additional first-class agent-provider integrations or a replacement custom chat interface; generic launch profiles remain available in the basic workflow.
- Remote or cross-machine hosting, multiple users, an OS service/login startup, or simultaneous interactive multi-writer UI clients. The first host is local to the user with one controlling UI and explicit takeover.
- Guaranteeing uninterrupted live terminals across host crashes, sign-out or reboot; automatic agent restart, prompt replay or recovery rollback.
- A full general-purpose terminal multiplexer with arbitrary pane layouts, a command language or remote transport infrastructure.
- A separate workflow database, persistent terminal/event logs or automatic transcript copying. Durable workflow records remain in the combined application document, and provider transcripts remain provider-owned.
- New automatic setup/service/port recipes, task validation runners, full branch-review tooling, PR-creation forms, CI dashboards, review submissions or automatic merges beyond existing features. Tickets can be delivered and closed through externally managed pull requests without adding those other report features here.
- Interactive rebase, force-push, conflict resolution, history rewriting, expanded Git mutation parallelism or changing existing dirty-worktree/original-checkout protections.
- Universal control of unmanaged external tools or a guarantee that stopping an agent reverses previously completed edits or external side effects.

## Further Notes

- This specification combines the report's session-attention/resume and task-context proposals into one ticket-native workflow. The design interview explicitly selected a shared worktree per ticket and embedded Copilot hosting, rather than one worktree per task and external terminals for integrated sessions.
- The accepted decisions are default GitHub ticket-centered workflow (ADR 0003), shared ticket worktree and ownership (ADR 0004), native hosted Copilot terminals (ADR 0005), and the persistent local host with detachable clients (ADR 0006). The single combined-document and explicit-source decisions (ADRs 0001 and 0002) remain in force. The requirements above restate the decisions so the issue is self-contained.
- Source baseline reviewed: commit 4c5f31e. The current implementation has reusable Git/discovery/configuration modules and a background job loop, but no PTY host, persistent agent registry or client/host wire protocol. No live hosted Copilot or detach/reattach prototype has been validated during this design session.
- Primary documentation informed feasibility, not a tested compatibility claim: [tmux server/client lifecycle](https://github.com/tmux/tmux/wiki/Getting-Started#the-tmux-server-and-clients), [Microsoft pseudoconsole lifecycle](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [Copilot native-session extensions](https://docs.github.com/en/copilot/tutorials/create-an-extension), and [Copilot session events](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events). Copilot extensions are experimental, and some attention events are ephemeral; native terminal hosting and reliable event observation must be demonstrated together.
- Detailed transport/library choices, inspectable import syntax, internal schema layout, default keybindings/colors and resource bounds are implementation choices constrained by this specification. They must preserve the observable behavior, physical-checkout exclusivity and existing configuration semantics rather than reopen the product design.
- This is one complete feature specification. An implementation agent may stage the work behind the host interface, but the feature is not complete until the ticket workflow, native UI, attention, ownership, background lifecycle, recovery, cache, cleanup and opt-in notifications work together as specified.
